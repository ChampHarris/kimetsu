# Spec approval

Since 2026-10-28 Champ delegates spec approval (`docs/tools/decision-rights.md`): an outside review approves a spec, and Champ judges the result by playing it (`docs/playtest.md`). Before that, only Champ approved (D-030).

## When a spec is reviewed
At the end of a turn (the Stop hook), every spec in `docs/design/specs/` is checked. A spec is ready when all three hold:
- `status: REVIEW`;
- `python tools/check_spec.py` passes;
- every item under "Open Questions for Champ" is answered, as `**Champ, YYYY-MM-DD: ...**` or `**Claude, YYYY-MM-DD: ... (delegated)**` (or the section has no numbered questions).

The hook then tells Claude to run the red-team agent with exactly the prompt `Spec approval review: <path>, Spec <id> (rev <8 hex>)` (without the quotes the message shows) and nothing else. Each revision is sent once; an edit makes a new revision, which comes back. While the review runs, Claude leaves the project's files alone and sends the agent nothing: a file it read changing under it, or any message, refuses its APPROVE.

## What APPROVE does
The red-team agent ends with `Spec <id> (rev <rev>): APPROVE` only when it found nothing at pillar-breaking or exploit level. A SubagentStop hook records it in `.claude/.state/spec_approvals.json` (gitignored) only when all of these hold:
- that verdict is the last line of the agent's answer: the report of its newest `SubagentHandback` call (how a background agent answers; its payload then has no last message at all, D-129), else its last message, else the last text in its transcript. A verdict quoted anywhere else doesn't count;
- the verdict names the spec and revision the prompt asked about, and nothing the agent wrote (its reports and its text) has a NOT YET written next to that spec and revision: as the verdict line in bold, after a dash, in lower case, as `NOT_YET`, with a backticked id, `rev:`, `verdict:` between, `Spec <id>, rev <rev>: NOT YET` or `NOT YET: Spec <id> (rev <rev>)`, the revision in either case. Away from the verdict line's own place `NOT YET` counts only in capitals as whole words, so English ("is not yet built") isn't read as a verdict. A NOT YET worded further from the spec and revision than that isn't seen;
- the spec is ready at that exact revision;
- the agent's transcript is whole (every line parses), holds the prompt (not a continuation from another session), shows it was given exactly the hook's prompt, and shows that only the harness's own records followed: an allowlist of the record and attachment kinds real reviews carry. Of what reaches the agent as words, only tool results, the harness's own reminders and the agent's own task notifications may follow. A message from the coordinator (a `SendMessage` to the running agent), a peer session or a human, a meta record that isn't a system reminder, a second prompt (a resumed review), a file in the project changed by someone else after the agent read it (the harness shows it a snippet), or a record or attachment of a kind the hook doesn't know all refuse;
- every turn of the review ran on the model `red-team.md` pins (`model: opus`), since the Agent tool can pick another model for one run;
- the spec file wasn't written after the prompt's timestamp, so a spec swapped for another text while the agent read it and put back is caught (unless its old mtime is restored too);
- the transcript is where Claude Code keeps this agent's: `subagents/agent-<agent_id>.jsonl`;
- no review said `NOT YET` at that revision, so a second review of the same text can't overturn one (no shopping for a verdict).

The red-team agent writes nothing in the project: to extend a sim it copies it to its scratchpad. Its own Bash writes reach it as an edited file, which refuses its APPROVE like anyone else's (D-133).

**NOT YET wins, and fails closed.** A review whose prompt names a spec and revision counts as NOT YET at that revision unless its answer ends in exactly that APPROVE: a cut-off review, another wording (`Verdict: fix first`, a bare `NOT YET`) or a sign-off after the verdict all count, since a wrong NOT YET costs only an edit. Every NOT YET is written first to an append-only ledger, `.claude/.state/spec_not_yet.jsonl`, then to the state file's lists, even from a steered, resumed or damaged review or a red-team run that wasn't an approval review, and a later report quoting an older revision's NOT YET never replaces a newer one. A NOT YET withdraws a review's approval already recorded at that revision (two reviews of one revision: the NOT YET wins whichever finishes first), and the guard reads both records, so even a lost state write can't let one through. Champ's own Approve stands over a NOT YET.

**The state file.** Every change to it happens under a lock file (`spec_approvals.lock`; one older than 30 s, left by a hook that died, is taken over). A hook that can't get the lock within 3 s records nothing (a NOT YET still reaches the ledger). A state file that can't be read, or has another shape than the hook writes, is never written over and nothing is recorded on it; the Stop hook says so until Champ deletes or fixes it (the ledger keeps every NOT YET).

**Refusals are shown.** A review the hook can't record is noted under `refused` with the reason. The next Stop reports it once, for a ready spec at that revision, and the guard's question names it if Claude tries the status edit anyway. Every stop the hook gets is logged first, the last five kept in `.claude/.state/subagent_stops.jsonl` (what the hook was given, how many transcript lines didn't parse, and whether it found a hand-back report), so a missing record can be traced. The guard then lets one Edit set the recorded revision to `status: APPROVED`, as long as the edit changes nothing but the status line. Claude follows it with a Decided row in `docs/decisions.md`, an update to `docs/state.md`, and the spec's feel and look calls in `docs/playtest.md`. After `NOT YET`, Claude fixes the findings and the new revision is reviewed again.

**Known limits.** A review the harness compacts mid-run is refused (its summary arrives as a second user message), and so is one the runtime moves to another model mid-run, or one with a `<synthetic>` turn (what Claude Code writes after an interrupt; none in 175 real subagent transcripts). Any edit makes a new revision, so the no-shopping rule binds the same text only. A spec swapped and put back with its old mtime restored isn't caught. A refusal made because the lock was held isn't saved (only stderr says it; the guard still asks). Two hooks taking over one stale lock at once can both hold it; the ledger keeps every NOT YET, so that can't let an approval through. The main session could still steer a review through the repository files the agent reads before it starts; that's the design's limit, not the hook's.

The main session can't approve its own spec: only the hook writes the record, from the red-team agent's message. Anything else that tries to set APPROVED (no record, another revision, other changes in the same edit) gets a permission prompt, and approving that prompt is Champ approving it. The shell can never set APPROVED. The guard reads the status both ways a reader can (its own front-matter parse, the first status line, and check_spec's, the last), so a second status line, a front matter that only check_spec accepts, an added `status: approved` anywhere, or any spec Edit the guard can't place exactly (an `old_string` not in the file even with its `\uXXXX` escapes read, such as straight quotes against curly ones, which the Edit tool can still match) all ask (D-133). The guard copies the tool's other rule too: an empty `new_string` also drops the newline after `old_string`. Champ can still approve himself: a question whose whole text is "Approve spec <id> (rev <rev>)?" that he answers Approve is recorded the same way. The answer is read from the result's `answers` only, or from its text when it comes back as plain text, never from the echoed questions and options.

## Changing an approved spec
Set `status: REVIEW` in the same edit: that reopens it and it goes back through the review. The reopened spec keeps its `id` (a different id asks Champ: a different spec goes in its own file). An edit that keeps it APPROVED, or sets anything but REVIEW, asks Champ.

## Files and checks
- `.claude/hooks/spec_approval.py`: Stop (send to review), SubagentStop on `red-team` (record APPROVE, keep NOT YET, note refusals), PreToolUse and PostToolUse on `AskUserQuestion` (only "T3 " questions reach Champ; Champ's own Approve is recorded). It keeps the last five AskUserQuestion payloads in `.claude/.state/ask_payloads.jsonl`.
- `.claude/hooks/guard_paths.py`: `champ_approved()` checks the record (any source), the revision, a 24-hour limit, the status-only edit and, for a review's record, that no NOT YET exists at that revision (`_common.said_not_yet`: the ledger and the state file); its question names a refusal.
- `.claude/agents/red-team.md`: the "Spec approval review" section sets the bar.
- Test: `python .claude/hooks/tests/test_spec_approval.py`; `test_guard.py` covers the guard side.
